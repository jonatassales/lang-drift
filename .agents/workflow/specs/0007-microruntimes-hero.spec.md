# Microruntimes hero: a simulated planning session fills the ticket card

**Status:** ready-for-agent

## Problem Statement

The Microruntimes product page opens in the Vision page's mold: a centered question headline with a gradient highlight, a lead, two calls to action, then a terminal and a lifecycle card that do not talk to each other. A visitor who arrives from the Platform menu sees the same opening on three product pages and cannot tell, in the first twenty seconds, what a microruntime is or why it exists. The terminal types a session and the card beside it sits still, so the strongest material on the page, an `ex` session, explains nothing about the composition, the limits or the cost of a run.

## Solution

The page opens with an `h1` that reads only "Microruntimes" and, under it, a simulated terminal session on the left that drives a ticket card on the right. The session types `ex agent plan` with a ticket number, as if a person had, and the card fades in and fills line by line in the rhythm of the log: the ticket's artifacts (PRD, design doc, spec, guardrail), a suggested model and effort, five components resolved from the spec with the hardware share of each, a bounded envelope against a suggested one, and a closing report. The visitor watches and understands that a microruntime is the smallest infrastructure one ticket needs, planned from the ticket's own artifacts and bounded before anything runs. Nothing executes, nothing is paid for, and the copy never says otherwise: the planning lines carry a `console ›` prefix, the figures stay in millicores and MiB, and the final row is pending the team's authorization.

## User Stories

1. As a visitor, I want the Microruntimes page to open with the product name alone, so that the opening reads differently from the Vision and FinOps pages.
2. As a visitor, I want the terminal and the card to be the first thing under the heading, so that the product explains itself through its own session instead of a paragraph.
3. As a visitor, I want the terminal to play on its own when it is on screen, so that I watch a session without typing anything.
4. As a visitor, I want the card to appear only when the simulated command is entered, so that I read the card as the result of the command.
5. As a visitor, I want the card to show the ticket number large and the PRD, design doc and spec names as soon as it appears, so that I see the plan starts from the ticket's artifacts.
6. As a visitor, I want the suggested model and effort to start as a dash, turn into a skeleton while the console searches, and then show a value, so that I see where the recommendation comes from.
7. As a visitor, I want the artifacts to be marked read when the terminal reads them, so that cause and effect stay side by side.
8. As a visitor, I want the guardrail to appear with its criteria and the note that it is a review rule with no automatic enforcement, so that I do not read it as a gate that passed.
9. As a visitor, I want the bounded envelope to appear before any component, so that I see limits are set by the team before the plan sizes anything.
10. As a visitor, I want the components to appear as skeletons first and then one by one with a logo, a path, a kind, CPU and memory, so that I see the plan resolving the spec into concrete units.
11. As a visitor, I want a thin bar under each component showing its share of the CPU envelope, and a total that updates as components resolve, so that I see the plan consume the envelope.
12. As a visitor, I want a hardware table with CPU, memory, GPU and disk, bounded against suggested, so that I see the four resources I think about.
13. As a visitor, I want the GPU and disk rows to say that they are not `runtime.md` fields instead of showing a number, so that the page never claims a limit `ex` cannot set.
14. As a visitor, I want a line saying that no price source is configured and the figures stay in units, so that I do not expect a currency the plan cannot justify.
15. As a visitor, I want a closing report with the bounded figures, the suggested figures, the suggested materialization and a final row pending team authorization, so that I read the plan as a recommendation and not as spending.
16. As a visitor, I want a pause and replay control on the card, so that I can stop the moving content or watch the session again.
17. As a visitor who asked for reduced motion, I want the whole transcript printed and the card in its final state at once, with no pulse, no transition and no control, so that nothing moves without my consent.
18. As a visitor on a narrow screen, I want the heading, the terminal and the card to stack, the terminal to stay short enough for the ticket head to fit in the first screen, and no horizontal overflow at 375px, so that the hero works on a phone.
19. As a visitor in either color scheme, I want the technology marks to follow the text color, so that the card reads correctly in light and dark.
20. As a screen reader user, I want the hero's summary to describe the final plan and say that the session is simulated, so that I understand the hero without the animation.
21. As a screen reader user, I want only the closing report announced, once, when it fills, so that nineteen terminal lines do not interrupt me.
22. As a keyboard user, I want the pause and replay control reachable with Tab and operable with Enter and Space, with a visible focus ring, so that the control works without a pointer.
23. As a visitor reading pt-BR, zh-Hant, ja or vi, I want the whole hero in my language with the same structure, so that nothing depends on English.
24. As a visitor, I want the lifecycle steps and the evidence they leave to remain on the page, so that removing the old hero card loses no explanation.
25. As a search engine, I want the first frame without JavaScript to carry the heading, the terminal's transcript and the card's reserved space, so that the page indexes and never shifts its layout.
26. As a frontend developer, I want the terminal to report how many lines it has completed and to accept a paused flag, so that a sibling can be driven by the terminal's own clock.
27. As a frontend developer, I want one shared atom for the session, so that the terminal, the card and the control stay in sync without prop drilling from a Server Component page.
28. As a frontend developer, I want the card to derive every field from the number of completed lines and a static reveal table, so that the card owns no timer and cannot drift from the terminal.
29. As a frontend developer, I want the technology marks as icon components with the same interface as the platform icons, so that they follow the color scheme through `currentColor` and need no image files or attribution README.
30. As a frontend developer, I want the content module to lock the figures with tests, so that the shares always sum to the suggested totals and never exceed the envelope.
31. As a frontend developer, I want every new string in the JSON catalog with parity across the five locales, so that the localization checks stay green.
32. As the owner, I want the copy drafted in all five locales, so that I edit the catalogs rather than start from nothing.
33. As the owner, I want every line of the session to be defensible against what `ex` and the console do today, so that the hero never claims a shipped planner, a price list or a GPU limit.
34. As the owner, I want the Vision and FinOps pages untouched, so that this change restyles no sibling.

## Implementation Decisions

- **Opening.** The Microruntimes page composes its own hero section instead of rendering `ProductHero`: a landmark labelled by the `h1` "Microruntimes" with the current heading classes and no `ChromaText`, a screen-reader-only summary paragraph wired by `aria-describedby`, and the existing two-column grid with the session terminal on the left and the ticket card on the right. `ProductHero` is not edited; the FinOps page keeps using it. The skip link keeps its target.
- **Session terminal.** `MacTerminal`, the owned SmoothUI vendor component shared with the home page, gains three optional props: `onProgress`, called from an effect with the number of completed lines whenever that number changes, which also covers the reduced-motion branch that completes every line at once; `paused`, joined into the existing play condition beside viewport and page visibility; and a `warning` line type in the warning status color. Nothing changes for callers that pass none of them. A thin client wrapper, `SessionTerminal`, maps the session's line ids to catalog text, keys the terminal on the run counter so a replay remounts it with a fresh machine, caps its height with a viewport-relative clamp so the ticket head fits in a phone's first screen, and binds `onProgress` and `paused` to the session atom; the page stays a Server Component and passes no function.
- **Typed command.** The session opens with `ex agent plan 0031-TICKET-early-access-runtime`, typed at the terminal's default speed. `ex agent plan` is the intended entry point under the real `ex agent` family and does not exist today; the second line, `# plan only · nothing is built, started or paid for in this step`, frames the session, every reasoning line carries the `console ›` prefix so the connected agent is the transport and the console is the thinker, and the summary names the session as simulated. The documentation does not list the subcommand as available.
- **Session script.** Nineteen lines in this order, each with a kind and a delay: the typed command; the plan-only comment; `console › RAG over project episodes · a model and effort for this ticket`; `console › 3 episodes cited · none with measured resources`; `✓ suggests operator/allowed-model · effort medium`; `reads` for the PRD, design doc, spec and ticket; `reads` for the guardrail with its criteria; `bounded cpuMillis 2000 · memoryMiB 3072 · set by the team in the design doc`; `console › resolving 5 components named in the spec · paths, images, ports`; five `✓` component lines (Go api, Node.js api, NATS broker, Redis cache, Next.js web) with path, kind, CPU and memory; `✓ size` with the suggested totals, `5 one-replica Deployments` and `proposed shares`; the warning `limits gpu and disk are not runtime.md fields · none requested`; `estimate no price source configured · figures stay in millicores and MiB`; `✓ plan runtime.md draft, revision 1 · proposed to the console`; and the closing comment that once the team authorizes, `ex agent run` applies the recorded intent. The word RAG appears once, on the memory line, attributed to the console; the summary calls that step proposed. The session lasts between fifteen and twenty seconds.
- **Ticket card.** A client article that is in the DOM from the first paint as invisible with zero opacity, so the grid row reserves its height, and becomes visible with a motion-safe opacity transition when the typed line completes. Regions from top to bottom: the ticket head (eyebrow, the number as the only large type, the slug, the title, a `ready-for-agent` chip, a read mark); a two-column definition list with PRD, design doc, spec and guardrail; the suggested model and effort cells with a `recommendation · the team authorizes` note; the components manifest with a dash row, then skeleton rows, then filled rows each carrying a technology icon, the path, a kind chip, CPU and memory and a two-pixel share bar of the CPU envelope, closed by a running total; a real table with resource, bounded and suggested columns for CPU, memory, GPU and disk, with headroom bars on CPU and memory, `none` and a dash on GPU and disk with the note `not a runtime.md field`, and the line `price basis: none configured · units only`; and the report as a detail list with bounded, suggested, suggested resource (`5 one-replica Deployments`) and final (`1,450m · 2,304 MiB · pending team authorization`), a footer line naming the `runtime.md` draft proposed to the console, and the pause/replay control. The report footer is the card's only live region. Skeletons and bars are plain Tailwind spans local to the card; no shared primitive is added for them.
- **Figures.** Bounded envelope 2,000 millicores and 3,072 MiB. Components: Go api 250m and 256 MiB, Node.js api 300m and 512 MiB, NATS broker 200m and 256 MiB, Redis cache 200m and 256 MiB, Next.js web 500m and 1,024 MiB; suggested totals 1,450m and 2,304 MiB; shares 12.5, 15, 10, 10 and 25 percent of the CPU envelope; headroom 72.5 and 75 percent. Units only, formatted with `Intl.NumberFormat` for the locale; no currency anywhere; unknown values are a dash, never zero. Unequal shares describe a proposed allocator, and the size line says `proposed shares`; today's connected agent splits the envelope equally.
- **Artifacts.** PRD `0002-PRD-early-access.prd.md`, design doc `0005-DD-early-access-runtime.dd.md`, spec `0011-SPEC-early-access-runtime.spec.md`, ticket `0031-TICKET-early-access-runtime` titled "Run the early-access sign-up use case as a microruntime", guardrail `0001-finops.gr.md · FIN-02 · FIN-04` with the note `review rule · no automatic enforcement`. The names follow the `ex init` scaffold and avoid this repository's own numbers. The model name is `operator/allowed-model`, the placeholder the runtime file editor already uses; effort uses the `runtime.md` tokens low, medium and high.
- **State.** One atom, `microruntimeSessionAtom`, in its own atom module and re-exported by name from the state barrel, shaped `{ playedCount, paused, run }`. The session terminal writes `playedCount` through `onProgress`; the control writes `paused` and, on replay, resets `playedCount` and increments `run`. The card reads `playedCount` and derives every field from it and from two static tables in the content module: the ordered session (`planSession`) and a reveal table mapping each card field to the line that reveals it. A field shows once the count passes its line; the model and effort skeletons live between the memory line and the suggestion; component row skeletons live between the resolve line and each component's line; running sums add the rows already passed. The card owns no timer and no copy of the sequence. Under reduced motion the terminal completes every line at once, the progress effect reports the total, the card renders its final state with no pulse and no transition, and the control is not rendered. Scenario tabs elsewhere on the page keep local state.
- **Technology icons.** Five new icon components in the web package, Go, Node.js, NATS, Redis and Next.js, with the same interface as the platform icons: a `className` prop, a 24-unit viewBox, strokes and fills in `currentColor`, `aria-hidden`, exported by name from their own barrel and entry in the package export map. The marks are simplified monochrome renderings; the technology name always sits in HTML beside the mark in the component row, so the icon is decorative.
- **Lifecycle steps.** `LifecycleDemo` leaves the hero and is deleted with its test. Its six-step stepper and the "What it does / Evidence it leaves" panel are extracted into `LifecycleSteps`, mounted in the evidence section above `StageEvidence`, still writing `selectedLifecycleStageAtom`, so the evidence record keeps a writer and no live region goes stale. This is the only change outside the hero, forced by removing the old card. The runtime descriptor, the execution ledger and the stage evidence paths in the content module stay as they are.
- **Copy and data.** The Microruntimes catalog, five locales in one file in the same key order, shrinks `hero` to a title and a summary and gains a `session` family: the terminal's title, label and nineteen line texts, and the card's labels, kinds, column heads, ICU totals, hardware labels and notes, report rows, control labels and value formats. The catalog keys only `LifecycleDemo` used are removed; the lifecycle family keeps what `LifecycleSteps` needs. Product and technology names, `ex`, `runtime.md`, the model placeholder, the effort tokens, file names, paths, the guardrail criteria and the artifact numbers stay untranslated inside translated sentences. The content module holds what is not a sentence: the session's ids, kinds and delays, the ticket plan (artifacts, components with path, technology, kind and figures, the envelope, the suggested totals, the draft path) and the reveal table, with the catalog's TypeScript shape typed from the id arrays.
- **Motion.** Autoplay follows the terminal's existing rule: at least 35 percent on screen and the tab visible. The card fades in over 500 milliseconds with no translate; a dash becomes a skeleton with no transition; a skeleton becomes a value with a 300 millisecond opacity transition; bars grow with a 700 millisecond width transition; figures appear as text with no count-up. Every transition is motion-safe. Pause and replay are a text button in the card's footer; the terminal and the card pause together when the hero leaves the viewport.
- **Metadata and routes.** Unchanged. The page keeps its title, description, canonical, hreflang, social images and sitemap entries.
- **Workflow.** One commit per ticket on a `feat/` branch with its `Ticket:` trailer and no AI attribution lines, then a pull request into `main`.

## Testing Decisions

A good test checks what a visitor or a build sees: rendered text, ARIA state, the store value after a click or after the terminal advances, a catalog's parity. It never asserts class names or internal structure.

Seams, highest first:

1. **Catalog parity** (existing seam): the Microruntimes catalog stays in the family list of the website's catalog test, which checks keys, ICU arguments and rich tags against `en` and formats every message with counts 0, 1, 2, 3 and 12 in every locale.
2. **Content module** (existing seam, new assertions): the component figures sum to the suggested totals; the suggested totals stay within the envelope; every component has a session line; every reveal points to a real line id; delays are positive and the session lasts between fifteen and twenty seconds at the default typing speed; exactly one line is the typed command.
3. **Web primitives** (existing seam): `renderToString` tests like the platform icons' test for the five technology icons (an `svg` with `aria-hidden`, the class prop applied) and a jsdom test for `MacTerminal` with an intersecting `IntersectionObserver` stub, a `matchMedia` stub and fake timers, asserting that `onProgress` is called with 1, 2 and so on as lines complete, that `paused` stops the count, and that the reduced-motion branch reports the full line count.
4. **Demos** (existing seam): jsdom tests with Testing Library inside a fresh Jotai `Provider`, as the lifecycle demo and the voice preview tests do. The ticket card at count zero is invisible and shows the artifact names and dashes; after the memory line the model and effort cells show skeletons; after the suggestion they show the placeholder model and `medium`; after the first component line the row shows its path and figures and the total reads one of five resolved; at the full count the report shows the suggested totals and the pending authorization text and the control reads replay; clicking replay resets the store to count zero with the run counter incremented. The session terminal wrapper, with the same stubs and fake timers, increments the store's count as lines complete. The relocated lifecycle steps keep their existing test: `aria-current` moves, the atom follows, the panel text changes.
5. **Repository checks**: `pnpm turbo run check`, `pnpm turbo run typecheck test --filter=website --filter=@langdrift/web`, `pnpm turbo run build`, `drift check localization`, `drift check dead-code`.

Manual verification in the built-in browser: the hero in the five locales with the same structure, both color schemes, 375px without horizontal overflow and with the ticket head in the first screen, reduced motion showing the final card and the full transcript with no control, keyboard operation of pause and replay with a visible focus ring, the first frame without JavaScript showing the heading, the terminal frame and the reserved card without a layout shift, one announcement of the report at the end, and the Vision and FinOps pages unchanged.

## Out of Scope

- Any section of the Microruntimes page beyond the hero, except mounting the relocated lifecycle steps in the evidence section.
- Aligning the runtime descriptor shown in the runs section (`checkout-preview`) with the ticket planned in the hero (`early-access-runtime`).
- A real `ex agent plan` subcommand, a cost ledger, a price source, a GPU or disk field in `runtime.md`, or any console feature; the hero describes the intended planning flow with illustrative figures in units.
- Documentation changes, including a note that planning from a ticket is proposed.
- The Vision and FinOps pages and the shared `ProductHero`.
- Image files, an attribution README or a third-party icon dependency for the technology marks.

## Further Notes

The planning lines describe the upstream console's recommendation service (a vector search over project episodes) and a proposed allocator; neither lives in this repository, and `ex` makes no model call, computes no cost and runs no retrieval today. The copy keeps the console as the thinker and `ex` as the transport, and the closing comment names `ex agent run`, which is real, as the step that applies recorded console intent once the team authorizes. The owner has removed visible illustrative disclosures from this page (ticket 0045); the screen-reader summary is where the word simulated lives.
