# SDD guardrail

**Local policy v1, advisory since October 11, 2026.** Apply the [operating rule](../rules/0001-sdd.rule.md) to local software commits and PR delivery. This policy adds warning-level traceability checks, not organizational adoption, a workflow engine, or server-side controls.

| ID | Criterion | Evidence |
| --- | --- | --- |
| SDD-01 | Each commit belongs to one ticket. | The proposed/recorded message, one resolvable stable ticket ID in the index/commit tree, and review of the actual change scope. |
| SDD-02 | Each PR belongs to one spec and its tickets belong to that spec. | The actual PR's `Spec:` declaration, resolved spec and ticket relationships, and semantic scope review. Local pre-push cannot establish actual PR metadata. |
| SDD-03 | Pre-push reports traceability across outgoing work. | Supplied ref updates, deduplicated commit identities, association findings, and explicit coverage limitations. New refs use all locally reachable history; tags and deletions are identified separately. |

## Assessment and action

Use the SDD assessment vocabulary stated below. The former shared guardrail index is unavailable; the local SDD definitions and advisory exception remain explicit here:

- `compliant`: sufficient evidence meets the criterion for the recorded scope. A resolved ID alone does not prove semantic alignment or a PR association.
- `non-compliant`: evidence demonstrates a missing, duplicate, conflicting, or unresolved association. Warn and identify the correction.
- `not-verified`: required evidence is unavailable, including actual PR metadata before publication, incomplete history, or checker failure. Warn and record the limitation.
- `not-applicable`: the criterion does not apply to this operation, with rationale; for example, a deletion-only push adds no source commit to inspect.

Record policy/version, criterion, target revision or snapshot, owner, method, result, and limitations in the existing spec/ticket or review. Review actual PR evidence when available: a PR declaring a different spec than its tickets is `non-compliant`, not inferred compliant from local hook success. Without a PR, SDD-02 remains `not-verified`; creating one is not a condition for local tooling completion.

**Severity is independent of assessment.** SDD failures, missing evidence, and checker errors warn for now. This is the explicit SDD exception to generic missing-evidence blocking language; it does not approve the missing evidence. It does not weaken FinOps, Twelve-Factor, permissions, or the blocking Conventional Commit, lint, build, and test checks.

The hooks never change ticket state, approve a spec, certify a release, contact a hosting API, or infer an organization's acceptance. A policy change to blocking SDD enforcement requires a separately authorized cycle.
