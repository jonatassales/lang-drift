# Concepts

LangDrift FinOps brings three ideas together: make costs part of delivery decisions, give agents useful context, and keep execution composed around the team's existing stack.

## FinOps: connect work and cost

The proposal connects covered spending to accepted outcomes and the team's authorized budget. Estimates support decisions; they are not promises of revenue or savings.

**Funding belongs to the team.** Features receive adjustable estimates and allocations. Developers and tickets do not receive independent spending grants. Planning, retrieval, review, retries, and execution must declare which costs they cover.

Historical evidence can improve an estimate. Unused budget alone does not establish savings. These docs describe this model; the platform does not implement a financial ledger or spending gate.

## Agent-assisted delivery: context before execution

Useful agent work starts with intent, ownership, constraints, and evidence. The proposed delivery flow carries that context through planning, implementation, verification, and review.

Leadership supplies objectives. Teams contribute operational evidence. DevEx helps people resolve tradeoffs; an LLM does not make delivery commitments on their behalf.

**Recommendation is not authorization.** An agent may estimate, recommend and execute permitted work; a deterministic control decides whether a paid or risky action is allowed.

## Microruntimes: compose around existing applications

A **microruntime** is one console-defined workload unit that `ex` runs on the project's local cluster: its configuration, execution and cleanup. Consumers choose their stack, components, and composition. Application source remains with its application.

For example, a unit named `website` would reference `apps/website`. It would not move the website into a platform-owned source tree.

The connected agent materializes native Kubernetes configuration for images, resources and replicas, and Terraform configuration for the namespace and quotas. The authored runtime file connects those authorities rather than duplicating their editable values. Resource quotas do not establish monetary limits or observed capacity.

## Contracts and evidence

Specifications state intended behavior. Gherkin can express examples without requiring BDD. Neither a specification nor a passing test proves a running production integration.

Every lifecycle operation keeps token-free **evidence** for later audit, and an **execution ledger** records what an operation created before its side effects, so cleanup acts only on what the ledger owns. Unknown state stays unknown; it is never reported as a confirmed stop.
