# Console rules

How a runtime executes and what the console's runtime view shows of it. Loaded in every session.

1. **The simulation is the source of truth.** The session that plays on the website's home defines how a runtime executes: `dft agent plan <ticket>`, then `dft agent run`, in the terminal beside the Ticket, Analysis, Plan and Workflow panel. The product executes as it does: the same steps, in the same order, with the same information. A spec or ticket that disagrees with it yields to it. It defines behavior, not code: its implementation follows these rules like any other. It lives in `apps/website/src/app/[locale]/(pages)/platform/microruntimes/`, its copy in `microruntimes.json`.
2. **The runtime view is the panel, nothing removed and nothing added.** What the console shows of a runtime's execution, live, is what the simulation's panel shows: every section and field, carrying the values of the real execution. An execution started with `dft` in a terminal appears in the console's runtime view, the same as one started from the console. The console's labels for stub or illustrative data are provenance, not information about the execution, and stay.
3. **Layout is free.** The console lays the panel out as a wide screen, like Vercel's deployment view, and may arrange, group and size its parts differently from the website, without renaming or reinterpreting any of them. Information the console needs and the panel lacks enters the simulation first; the console follows.
4. **Every ticket aligns with the simulation.** What the code does beyond the simulation is removed. What the simulation shows and the code lacks becomes a new ticket that builds it. What differs is both. A ticket's acceptance criteria quote the exact terminal lines and card fields it must produce. ADR 0005 (Perfect Simulation Alignment) records this.
